## 1. 项目总体目标

开发一个可交付个人使用的 **Windows 桌面软件**，批量采集**本人** TikTok 账号的作品链接：
导入账号 → 选择日期 → 选择账号 → 设置采集数量 → 严格串行采集 → 保存结果 → 复制/导出。

**关键边界**：这是「链接采集工具」，不是「视频下载工具」。只获取作品页面 URL，不下载视频。

**产品定位**：个人/小规模使用，实际账号规模约 **30～40 个**。不做企业级 SaaS，架构保留扩展性但 UI/交互复杂度围绕 30～40 账号设计。

### P44 采集任务按地区选择账号

- **交互**：账号选择区顶部新增「地区」下拉。**切换地区 = 自动勾选该地区下的全部账号**（替换式），
  因此「选越南 → 点开始采集」一步完成；选「全部地区」即不分类全采。
- **关键实现**：勾选状态从「读控件」改为**独立保存的 `_checked_ids` 集合** ——
  切换地区会重建列表，若仍读控件状态，跨地区的选择与数量输入都会丢失。
  配套保存 `_count_values`（每账号数量）与 `_known_ids`（识别新增/删除账号）。
- **勾选延续规则**：首次进入默认全选（保持原有习惯）；之后重新加载时保留用户选择，
  新增账号默认勾选、已删除账号自动剔除。
- **`_selected_accounts()` 与当前筛选无关**：返回所有已勾选账号（跨地区），
  保证「筛选只影响显示、不影响采集范围」。
- 无匹配地区时显示专门提示（与「暂无启用账号」的空状态区分）。
- **验证**：224 单测全绿；8 页冒烟 PASS；账号页 36 项 + 采集页 **21 项 UI 检查**全 PASS。

### P43 账号昵称（辨识账号）

- **数据来源**：主页首屏 `/api/post/item_list/` 响应里的 `author.nickname`
  （探针实测确认；SSR 数据里没有该字段）。**零额外请求**，代价只是打开一次主页。
- **两条获取路径**：
  1. 采集时自动写回（`engine._collect_once` 从首个带昵称的作品上取，写入 `accounts.display_name`）；
  2. 账号管理页「刷新昵称」按钮 —— 有勾选处理勾选项，未勾选处理全部，后台线程执行 + 进度提示。
- **数据库**：新增 `Database.set_account_display_name()` —— **单列 UPDATE**，
  避免 `update_account()` 的整行覆盖误伤 region 等字段；值未变化时不写库。
- **界面**：表格新增「昵称」列（紧随账号列）；新增「刷新昵称」按钮；
  取不到时弹错误对话框说明可能原因（登录失效 / 无公开作品 / 风控）。
- **配套修正**：`AppServices.close()` 增加 Playwright 停止逻辑（此前只关数据库，
  浏览器驱动子进程可能残留）。
- **验证**：224 单测全绿（新增 9 个：解析昵称 2 + 单列更新 5 + engine 写昵称 2）；
  35 项 UI 检查 PASS；真实环境成功取到 3 个账号昵称。

### P42 重新抓取丢链接（根因修复）

- **现象**：用户回填链接时发现「少了两条链接」，且拿到的不是最新作品。
- **根因 A · 跨运行去重**：`CollectEngine.run()` 旧实现为
  `dedup = VideoDedup(initial=self.db.load_all_video_ids())` —— 把**全库已有 video_id**
  装进去重器，采集时命中即跳过并继续往后捞更旧的，于是
  ① 结果不是最新的（与「从最新开始拿」相悖）；② 数量可能凑不够。
  另外 `_collect_account` 重试时复用同一个去重器，第 2 次尝试会把第 1 次已采到的全部跳过。
  实证：部署库 `collect_logs` 中有 **40 条** `重复作品跳过` 记录，全部 `videos` 表**未入库**。
- **根因 B · 首屏响应被静默丢弃（更隐蔽，实测为主因）**：
  `ProfileCollector` 在 `provider.load_profile()` **返回之后**才注册
  `page.on("response")` 去捕获 `/api/post/item_list/`。而首屏那次响应就是**最新一批作品**，
  页面有缓存时 < 1s 即返回 → 监听器错过它，采集器只能捡到滚动后加载的**更旧作品**。
  实测证据：同一账号连采两次分别拿到 9/26 与 9/21 两批作品，且 `duplicates=0`、数量仍是满的
  —— 从日志上完全看不出异常。
  **通用规则：凡「监听响应再处理」的场景，监听必须在 `page.goto` 之前注册。**
  （`app/chat/provider.py` 一直遵守此规则，作品采集模块漏了。）
- **修复**：
  1. `engine.run()` 不再加载库中已有 ID；去重集合改为在 `_collect_once` 内**每次新建**
     （范围 = 本账号 + 本次采集，仅用于处理置顶作品在列表里重复渲染），重试时自然重置。
  2. `TaskRunner` 同步修改：移除 `dedup` 共享参数，每次尝试传 `VideoDedup()`。
  3. 统一 `engine._collect_once` 与 `collect_logic.collect_for_account` 的判断顺序
     （先去重、后数量检查），保证 `duplicates` 诊断准确。
  4. **监听提前到导航之前**：`TikTokProvider.load_profile(context, username, on_response=…)`
     在 `page.goto` 之前注册响应监听，确保首屏最新一批不被丢弃。
  5. 补可观测性告警：账号未捕获到任何 item_list 响应、或作品顺序非时间倒序时写 warning
     （这类静默失败此前在日志里毫无痕迹，是排查困难的根源）。
- **语义确认**（用户 2026-09-27 要求）：不管作品是几号的、今天有没有采过，
  每次都从最新一条开始依次取满指定数量；重新抓取 = 重新拿下来。
- **验证**：215 单测全绿（新增 3 个 engine 回归：连续两次结果一致 / 库中有更旧记录时仍取最新 /
  同一次采集内重复只算一次）；`diagnostics/verify_rerun_same.py` 真实环境连采两次结果完全一致
  （修复前同一账号两次分别拿到 9/26 与 9/21 两批，修复后两次均为最新那批）。

### P41 账号地区分类（要点）

- **数据库迁移红线**：`Database._migrate()` 在 `user_version != SCHEMA_VERSION` 时会 **DROP 所有业务表重建**，
  因此**新增字段绝不能靠递增 SCHEMA_VERSION**（那等于清空用户的账号/作品/登录记录）。
  统一走 `_ensure_columns()`：`PRAGMA table_info` 检查 → 缺列才 `ALTER TABLE ADD COLUMN`，幂等且不动版本号。
  新增字段一律登记在 `Database._EXTRA_COLUMNS`。
- **地区模型**：`accounts.region TEXT`（单值，空串 = 未分类）；常量与显示/解析工具在 `app/core/regions.py`。
  预置越南/缅甸/泰国/印度尼西亚/菲律宾/马来西亚/新加坡/柬埔寨/老挝；用户输入的任意地区名会自动进入所有下拉框。
- **显示名约定**：`account_label(row)` → `越南 · @user`（无地区则 `@user`）。
  ⚠️ 采集页/结果页/聊天页原先用 `lstrip("@")` 反解账号，加前缀后必须改用 `account_id_from_label()`，否则会解析失败。
- **服务层**：`AccountService.set_regions / region_options / region_stats`；`add / import_many / update` 均支持 `region`。
  ⚠️ `update()` 必须显式回填 region —— `update_account()` 是整行覆盖式 UPDATE，漏掉会把地区清空（已有回归测试）。
- **界面**：表格新增「地区」列（紧随账号列）；顶部地区筛选下拉；操作行地区统计；「设置地区」批量归类弹窗；
  添加行与批量导入弹窗均带地区选择；列表默认按「预置地区顺序 → 自定义 → 未分类」聚集排序。
- **验证**：210 单测全绿（新增 21 个，含「旧库升级不丢数据」与「改采集数量不清空地区」回归）；
  28 项 UI 检查 PASS；用户真实库（21 账号 / 84 作品）副本升级验证零丢失。

### v1.1.0 关键事实（供后续维护）

- **聊天取链唯一可行路径**：`DivChatBox` 内卡片 → `__reactProps$*` 里的 `itemId` → `/api/im/item_detail/?itemId=` → 拼 `https://www.tiktok.com/@{author}/{video|photo}/{id}`。
  **不存在** `a[href*="/video/"]`；整页扫描会抓到会话列表/页头里的隐藏链接（曾导致「不管选哪个会话都拿到同一批错误链接」）。
- **顺序**：聊天窗口内垂直位置，最下面最新 → 按 `getBoundingClientRect().top` 降序取。
- **线程**：worker 线程禁止直接调 `after()` → 统一用 `BasePage.ui_call()` / 聊天页事件队列。
- **交互**：关键动作不用模态确认框（会因遮挡 + `grab_set` 造成「点了没反应」）。
- **布局**：任何空 `CTkFrame` 必须显式给 `width/height`（默认 200×200 会撑大父容器）。

## 7. UI/UX 改造计划（P31–P35）

> 详细审计见当轮《UI/UX 审计报告》。核心结论：**不是换色，而是产品化重构**。
